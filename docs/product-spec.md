Спецификация: AI Grocery Assistant Demo

Runtime-архитектура продукта остаётся одноагентной и управляется одним LangGraph workflow.

1. Цель

Создать рабочий веб-прототип AI-функции для приложения доставки продуктов.

Пользователь описывает блюдо или задачу естественным языком, например:

Хочу лёгкий ужин на двоих до $35. Без грибов, готовить не дольше 30 минут.

Система уточняет требования при необходимости, формирует рецепт, находит конкретные товары среди 10 000 SKU, проверяет наличие и ограничения, после чего автоматически собирает корзину.

Демо должно выглядеть как законченный продукт доставки, а не как технический прототип или AI-чат поверх таблицы.

⸻

2. Основной сценарий

1. Пользователь открывает приложение.
2. Видит реалистичную главную страницу продуктового магазина.
3. Переходит в AI Assistant либо сразу вводит запрос.
4. AI анализирует запрос.
5. Если данных недостаточно, задаёт один конкретный уточняющий вопрос.
6. Формирует нормализованный рецепт:
    * количество порций;
    * ингредиенты;
    * необходимый объём каждого ингредиента;
    * ограничения;
    * предполагаемое время приготовления.
7. Выполняет поиск по каталогу из 10 000 SKU.
8. Выбирает конкретные товары и количество упаковок.
9. Проверяет:
    * наличие;
    * итоговую стоимость;
    * соответствие бюджету;
    * аллергены и исключённые ингредиенты;
    * достаточность объёма;
    * разумность остатков.
10. При проблемах выполняет замену или повторный подбор.
11. Собирает настоящую корзину внутри приложения.
12. Показывает краткое объяснение выбора и рецепт.
13. Пользователь может менять корзину обычными средствами интерфейса.

Пример финального ответа:

Готово. Собрал лёгкую пасту с креветками на двоих за $31.74. Взял сливки 10% и упаковку пасты 400 г. Креветки были доступны только в упаковке 300 г, поэтому их немного больше, чем требуется по рецепту.

⸻

3. Формат демо

Десктопная веб-страница делится вертикально на две части.

Левая часть — приложение доставки

Визуально выглядит как запущенное на iPhone приложение:

* корпус или аккуратная рамка устройства;
* мобильная ширина;
* статус-бар;
* нижняя навигация;
* плавные переходы между экранами;
* настоящий интерактивный каталог;
* AI-чат;
* корзина;
* оформление заказа.

Интерфейс не должен копировать Wolt, Instacart или другой бренд. Нужен самостоятельный нейтральный бренд продуктовой доставки.

Правая часть — AI Inspector

Показывает работу LangGraph в реальном времени:

* текущий узел графа;
* завершённые этапы;
* ожидающие этапы;
* краткое содержимое входа и выхода узла;
* число найденных SKU;
* число кандидатов после фильтрации;
* используемую модель;
* latency;
* приблизительное количество токенов;
* причины retry;
* переход на fallback-модель;
* результаты серверной валидации;
* изменения корзины.

Inspector должен быть понятен человеку без технического образования, но достаточно содержателен для технического питча.

Не показывать полный системный промпт, API-ключ, скрытые рассуждения модели или огромные JSON-объекты.

6. Каталог из 10 000 SKU

При первом запуске локальный генератор создаёт ровно 10 000 товарных записей с фиксированным seed.

Не генерировать каждую карточку через LLM. Реализация должна использовать процедурный генератор на основе:

* категорий;
* товарных семейств;
* брендов;
* вариантов;
* вкусов;
* размеров;
* форматов упаковки;
* диапазонов цен;
* шаблонов описаний;
* ингредиентов;
* аллергенов;
* условий хранения.

Каталог должен сохраняться в базе и не пересоздаваться при каждом запуске.

Реалистичная грязь в данных

Каталог не должен выглядеть идеально синтетическим.

Воспроизводимо добавить:

* отсутствующие описания;
* разные способы записи веса;
* отдельные опечатки;
* непоследовательную капитализацию;
* массу только в названии;
* пустой бренд;
* несколько дублей;

* неполный состав;
* неточный перевод;
* старую цену без активной скидки;
* нулевые остатки;

* смешанные единицы измерения;
* странные маркетинговые формулировки;
* редкие слишком короткие описания;
* товары с почти одинаковыми названиями.

Ошибки должны выглядеть как дефекты реального контент-менеджмента, а не как случайный мусор. Критически повреждённые записи не должны превышать примерно 1–2% каталога.

7. Поиск по каталогу

Не отправлять 10 000 товаров в контекст модели.

Использовать гибридный retrieval:

1. Нормализация запроса.
2. Определение необходимых ингредиентов.
3. Фильтрация по категории, наличию, аллергенам и цене.
4. Полнотекстовый поиск по:
    * названию;
    * бренду;
    * синонимам;
    * описанию;
    * ингредиентам.
5. Семантический поиск при необходимости.
6. Объединение и reranking результатов.
7. Передача модели компактного списка кандидатов.

На один ингредиент передавать ориентировочно 8–20 кандидатов. Общий размер shortlist для обычного запроса не должен превышать примерно 100–150 товаров.

Векторный поиск не должен быть обязательным для запуска. Основной рабочий сценарий обязан работать на локальной базе и полнотекстовом поиске. Embeddings можно добавить как дополнительный слой.

⸻

8. LangGraph

LangGraph используется как реальный оркестратор, а не декоративная зависимость.

Состояние графа

type GroceryAgentState = {
  sessionId: string;
  locale: "en" | "ru";
  conversation: ChatMessage[];
  userRequest: string;
  interpretedRequest?: {
    servings?: number;
    budget?: number;
    maxCookingTimeMinutes?: number;
    excludedIngredients: string[];
    allergies: string[];
    dietaryPreferences: string[];
    requestedDish?: string;
  };
  clarification?: {
    required: boolean;
    question?: string;
  };
  recipe?: RecipePlan;
  ingredientRequirements?: IngredientRequirement[];
  searchCandidates?: ProductCandidate[];
  selectedItems?: SelectedCartItem[];
  validationErrors?: ValidationError[];
  cart?: Cart;
  activeModel?: string;
  retryCount: number;
  inspectorEvents: InspectorEvent[];
};

Узлы графа

START
  ↓
interpret_request
  ↓
needs_clarification?
  ├─ yes → ask_clarification → wait_for_user
  └─ no
       ↓
plan_recipe
       ↓
normalize_ingredients
       ↓
retrieve_products
       ↓
select_products
       ↓
validate_selection
       ├─ valid → build_cart
       ├─ repairable → repair_selection → validate_selection
       └─ repeated failure → fallback_model
                                  ↓
                           validate_selection
                                  ↓
                              build_cart
                                  ↓
                         compose_user_response
                                  ↓
                                 END

Требования

* каждый узел создаёт событие для AI Inspector;
* состояние сохраняется между сообщениями;
* уточнение приостанавливает граф и продолжается после ответа;
* retry ограничен;
* повторная попытка получает только ошибку и необходимые данные;
* граф не должен бесконечно циклироваться;
* каждый переход логируется;
* серверные функции выполняют расчёты, а не LLM.

LangChain допустим для:

* model wrappers;
* tools;
* structured output;
* message abstractions.

Центральная orchestration-логика остаётся в LangGraph.

9. Использование моделей

Основная модель

OPENAI_PRIMARY_MODEL=gpt-5.6-luna

Используется для:

* понимания запроса;
* уточняющих вопросов;
* построения рецепта;
* выбора из shortlist;
* объяснения результата;
* изменения существующей корзины.

Fallback-модель

OPENAI_FALLBACK_MODEL=gpt-5.6-terra

Используется только когда:

* Luna дважды не прошла серверную проверку;
* запрос содержит несколько блюд и сложную оптимизацию;
* слишком много ограничений;
* подбор не укладывается в бюджет;
* confidence ниже установленного порога;
* structured output не получен после retry.

Модель Sol не использовать.

API

Использовать OpenAI Responses API и structured output/tool calling.

API-ключ хранится только на сервере:

OPENAI_API_KEY=
OPENAI_PRIMARY_MODEL=gpt-5.6-luna
OPENAI_FALLBACK_MODEL=gpt-5.6-terra

Ключ нельзя:

* отправлять в браузер;
* логировать;
* сохранять в репозиторий;
* показывать в Inspector;
* включать в ошибки клиентской части.

Если ключ отсутствует или модель недоступна, приложение должно показать понятную ошибку настройки. Не подменять реальный ответ заранее записанной AI-заглушкой.

⸻

10. Structured outputs

LLM никогда не возвращает корзину как свободный JSON-текст.

Использовать строгую схему:

const ProductSelectionSchema = z.object({
  selectedItems: z.array(
    z.object({
      productId: z.string(),
      quantity: z.number().int().positive(),
      ingredientKey: z.string(),
      confidence: z.number().min(0).max(1),
      reason: z.string().max(240),
    })
  ),
  unresolvedIngredients: z.array(z.string()),
  requiresFallback: z.boolean(),
});

Модель возвращает только:

* ID выбранного продукта;
* количество;
* привязку к ингредиенту;
* короткое объяснение;
* confidence.

Она не должна самостоятельно возвращать:

* цену;
* доступный остаток;
* итоговую стоимость;
* название товара;
* размер скидки.

Эти значения всегда берутся из базы по productId.

⸻

11. Серверная валидация

После каждого выбора проверить:

* продукт существует;
* продукт доступен;
* количество не превышает остаток;
* упаковки покрывают необходимое количество;
* нет запрещённых аллергенов;
* исключённые продукты отсутствуют;
* итог не превышает бюджет либо превышение явно согласовано;
* каждый обязательный ингредиент покрыт;
* одна позиция не добавлена несколько раз ошибочно;
* цена взята из текущей базы;
* весовые товары рассчитаны корректно.

Всю арифметику выполнять детерминированным кодом.

При ошибке модель получает компактное сообщение:

{
  "error": "budget_exceeded",
  "currentTotal": 41.82,
  "budget": 35,
  "replaceableItems": ["sku_104", "sku_890"],
  "allowedAlternatives": ["sku_233", "sku_441", "sku_912"]
}

Не запускать весь граф заново без необходимости.

12. AI Inspector

Inspector визуализирует настоящий execution trace.

Верхняя часть

* статус: Idle / Running / Waiting / Completed / Failed;
* используемая модель;
* время выполнения;
* число шагов;
* стоимость или оценка расхода;
* размер исходного каталога;
* размер shortlist.

Граф

Отображать узлы и связи LangGraph.

Состояния узла:

* pending;
* active;
* completed;
* warning;
* failed;
* skipped.

Активный узел заметно подсвечивается.

Event stream

Примеры событий:

Request interpreted
Detected 2 servings and a $35 budget
Recipe planned
7 ingredient requirements generated
Catalog retrieval
10,000 SKU scanned
486 passed deterministic filters
74 candidates sent for selection
Model call
GPT-5.6 Luna
Structured response validated
Selection validation
1 item rejected: contains excluded allergen
Repair attempt
Alternative selected from 5 candidates
Cart created
8 products · $31.74

Инспекция события

По клику показывать безопасные данные:

* входные параметры;
* результат;
* duration;
* число кандидатов;
* validation result;
* tool name;
* model name.

Не показывать chain of thought. Вместо него показывать краткое операционное объяснение.

17. Обязательные тестовые случаи

Happy path

Простой рецепт, все товары доступны, бюджет соблюдён.

Уточнение

Пользователь пишет только:

Хочу приготовить что-нибудь вкусное.

AI должен задать вопрос, а не произвольно собрать корзину.

Отсутствующий товар

Выбранный SKU заканчивается между retrieval и валидацией. Система находит замену.

Аллерген

Кандидат содержит запрещённый аллерген и отклоняется сервером.

Бюджет

Первая подборка превышает бюджет. Система заменяет самые дорогие позиции.

Сложный запрос

Несколько блюд и ограничений вызывают fallback на Terra.

Грязные данные

Описание неполное или масса указана только в названии. Система использует нормализованные поля либо отклоняет ненадёжную позицию.

Переключение языка

История и корзина сохраняются, интерфейс переключается с русского на английский.

18. Evals

Добавить небольшой набор воспроизводимых eval-кейсов.

Проверять не точное совпадение текста, а:

* корректность structured output;
* наличие необходимых tool calls;
* отсутствие выдуманных SKU;
* соблюдение бюджета;
* отсутствие запрещённых аллергенов;
* успешный fallback;
* отсутствие бесконечного retry;
* покрытие ингредиентов;
* корректное формирование корзины;
* сохранение состояния диалога.

Минимум 20 кейсов:

* 8 обычных;
* 4 с ограничениями;
* 3 с нехваткой товара;
* 3 бюджетных;
* 2 сложных с fallback.

⸻

19. Производительность и стоимость

Целевые показатели для обычного запроса:

* первый UI feedback — менее 300 мс;
* получение shortlist — менее 1 секунды;
* первый streaming-текст — по возможности менее 2 секунд;
* полная корзина — ориентировочно до 8–12 секунд;
* не более двух вызовов Luna в обычном сценарии;
* Terra не вызывается без конкретной причины;
* в LLM не передаётся полный каталог;
* повторная валидация использует только необходимые данные.

Системные промпты и стабильные инструкции должны быть компактными. Не дублировать в каждом вызове полные карточки товаров.

21. Definition of Done

Демо считается готовым, когда:

1. В базе действительно находится ровно 10 000 SKU.
2. Каталог можно просматривать и искать без AI.
3. Продукты распределены по полноценным категориям магазина.
4. AI работает через настоящий OpenAI API.
5. Основная модель — GPT-5.6 Luna.
6. Fallback — GPT-5.6 Terra.
7. LangGraph реально управляет сценарием.
8. Structured output проверяется через Zod.
9. Модель не получает весь каталог.
10. Корзина собирается из существующих productId.
11. Сервер проверяет цены, остатки, упаковки, бюджет и аллергены.
12. AI Inspector отображает реальные события графа.
13. Русский и английский интерфейсы полностью работают.
14. Все цены отображаются в USD.
15. Нет lorem ipsum и заранее записанных AI-ответов.
16. Основной сценарий работает после вставки API-ключа без ручного редактирования кода.
17. Проект проходит lint, typecheck и тесты.
18. Приложение визуально пригодно для записи презентационного видео и показа на питче.
